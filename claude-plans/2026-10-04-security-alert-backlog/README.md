# Security-alert backlog: diagnosis and plan

**Date:** 2026-10-04. **Status:** diagnosed. The cleanup waits on Kevin's okay and his four answers below. **Source:** a read-only workflow: five Sonnet readers across 15 repos, one Opus review of this repo's automation and one Opus synthesis, with load-bearing claims spot-checked by the orchestrator. The full per-repo evidence is in `evidence/diagnosis.json`.

## What we found

A live sweep on 2026-10-04 found about 330 open Dependabot alerts across 15 of khglynn's 40 live repos, 13 of them critical. This repo's automation exists and runs, but it closed few of them, for the reasons below.

## Root causes

1. Dependabot opened fixes, but nothing merges them. The automation only auto-merges in repos that are enrolled in repo-standards and also have a required check that has to pass. Only 2 of the 15 repos with alerts (eachie, ynai) are enrolled. In every other repo, a fix PR sits until a person happens to look.

> Evidence: Measured on 2026-10-04 with gh pr list. Untouched open security PRs: recordOS #2-4 and spotify-bulk-actions-mcp #4 (open since 09-11, 23 days), holting-safely #5 (09-19), hevy-mcp #2/#3 (both green), harness-atlas #1 (09-22), lunch-no-drop #1 (09-22), sheet-music #1-3, sync-bot #49 (green), google_workspace_mcp #23. Only eachie, festival-navigator, kevinhg-com, list-maker, ynai and repo-standards carry dependabot-automerge.yml. Merging the PRs that are already green would close every alert in sync-bot, harness-atlas and hevy-mcp, and most of google_workspace_mcp.

2. One stale grouped PR blocks every newer alert. Dependabot puts its security fixes into a single 'group' PR per repo. While that PR stays open, each new alert gets deferred to it ('Detected existing pull request for the dependency group … Deferring creation of a new pull request'). The PR is supposed to refresh to take in the new fixes, but it never does. So one forgotten PR quietly holds back everything that arrives after it.

> Evidence: Measured from Dependabot run logs. In holting-safely, 9 security jobs since 09-19 all deferred to PR #5, which covers anyio only and has not changed since 09-19. That leaves 30 of 31 alerts, both criticals included, with no PR. spotify-bulk-actions-mcp has the same pattern: PR #4 is frozen at 09-11 and 19 alerts (2 critical PyJWT/anyio) sit behind it. recordOS logged the same message on 09-29 and 10-01 (behind #2, which is red). ynai logged it on 09-29 and 10-01 (behind #18/#19, which are on hold as major updates), so the next.js critical never got a PR.

3. For about two-thirds of the alerts, Dependabot can't produce a fix at all. These are mostly 'transitive' packages, meaning packages pulled in by other packages rather than listed directly. Dependabot can't move them in three situations: (a) the project uses pnpm, (b) Cloudflare's wrangler/miniflare tools pin an exact older version, or (c) the files are in an old format it doesn't support. The README's fix (switch security updates off and back on) was already done on 09-22 and didn't help, because the jobs ran and failed. Only a manual lockfile refresh or an 'override' line clears these.

> Evidence: Measured from run logs. Ending in security_update_not_possible or dependency_file_not_resolvable: lunch-no-drop 16 of 17 jobs (pnpm; miniflare hard-pins undici 7.18.2), sheet-music 15 of 18 (pnpm, e.g. fast-uri resolvable only to 3.1.3 when the fix needs 3.1.8), remembrall 9 of 9 (wrangler and vitest-pool-workers pin undici at exactly 7.29.0), notion-souped-up-mcp 4 of 4 (vite stuck behind vitest), eachie ip-address (update_not_possible). Unsupported formats: starter (bundler v1) and trimmedia.github.io (grunt ~0.4 with no lockfile). Measured from the sweep file: four repos, lunch-no-drop 100, starter 75, sheet-music 74 and recordOS 44, hold 293 of the ~330 alerts.

4. The weekly check was never set up to see alerts. Its read-only token was never given permission to read Dependabot alerts. The digest also has no line that counts alerts. It treats a failed Dependabot run as 'fixes are running'. And it posts to Slack under Kevin's own name, which most likely means it never notifies him. Running out of Actions minutes was not the cause.

> Evidence: Measured: repo-standards/BUILD-LOG.md (2026-09-14) lists the AUDIT_READ_TOKEN permissions as Actions, Administration, Contents, Metadata and Pull requests, with no Dependabot alerts. repo-standards-audit/latest-digest.md:14 says 'security fixes could not be checked in 40 repos'. weekly-audit.yml:72 sends the error output to audit.log and never saves that file. On billing: since 09-20 there are 412 private runs and none of the failure notes mention a spending limit or minutes. ynai, sync-bot, eachie, remembrall and notion-souped-up CI all ran green through 10-03/04. One gap remains unexplained: there were no private runs at all on 09-26 and 09-27.
